## Mandatory offline KSP operating-condition validation gate (2026-11-27)

Before declaring any DLL suitable for installation or controlled flight testing, test representative user circumstances that can occur in KSP offline, including the actual production snapshot acquisition, admission, planning, control and failure/abort paths. Pure mathematical fixtures with preconstructed valid inputs, successful compilation and unchanged baseline failures are not sufficient. Build fixtures from actual KSP states, saved craft and captured runtime inputs where available; use realistic API semantics, explicitly distinguish valid zeros from unavailable data, and exercise the same production decision code rather than duplicating its checks in test-only code. Cover each supported starting regime (stable unpowered vacuum orbit, atmospheric entry, powered and unpowered descent, terminal approach), transitions, pressure/density/drag availability, engine activation and thrust authority, fuel/resource and crossfeed assumptions, vessel attitude/geometry, terrain/target, epoch/warp/ownership, cancellation/stale results and supported/unsupported equipment. Include representative valid cases that proceed and invalid cases that refuse with the correct reason. Require at least one complete representative supported orbit-to-contact case through snapshot admission, planning, independent replay, scenario validation and execution admission; exercise simulated actuator/control transitions offline. Preserve the distinction between offline model verification and actual Unity/KSP runtime parity; do not claim an untested API behavior is proven. Where real dependencies or evidence prevent realistic offline coverage, explicitly identify the missing case and treat the installation-readiness gate as unmet rather than using the user's flight as the first test of predictable conditions. Record the test matrix, exact commit, results, and outstanding limitations before recommending installation. This gate applies to experimental/test DLLs as well as production releases. Live testing remains necessary for actual physics and runtime behavior, not a substitute for predictable offline tests.

M5.6 supersedes prior explicit preview-only dispatch: ordinary Land at target on Duna automatically plans and engages only after existing validation/admission; refusal/abort stops without legacy fallback. No extra buttons or manual preview. Other bodies/untargeted unchanged. Prospective six-face stock drag estimate independent of live vacuum force; normal chute option allowed when no actual parachutes. Automatic log evidence. Mandatory offline validation gate remains in force.


## Vessel-independent targeted landing and reference-frame contract (2026-11-27)

The guidance SHALL land any physically capable vessel within the supported physics domain using runtime-acquired mass, usable propellant, thrust/flow/Isp and direction/torque authority, drag/lift, attitude response, resource connectivity and body/terrain parameters. No Eagle-specific tuning, craft-name checks, mass assumptions, or requirement for the player to supply configuration available from KSP. Where a material configuration fact cannot be determined from runtime or existing evidence, ask the user explicitly instead of guessing. The user's Eagle is an acceptance/regression case, not the design envelope. Test varied mass, TWR, propellant fraction, engine arrangements, drag and response, with both ordinary and high-crossrange targets. Large inclination changes are normal strategic landing work: search physically feasible finite plane-changing/deorbit and approach trajectories, including separate orbital plane adjustment when needed, fuel accounting and appropriate burn epochs. Never reject merely because the target is far outside the initial orbital plane or a fixed seed grid is inadequate; report genuine physical infeasibility separately from search exhaustion and improve/retry the search when resources/time permit. No minimum-throttle requirement or mandatory manual preparation. Normal workflow remains select target and Land at target; automatically plan and execute through observed contact. Existing numerical, control, reserve, ownership and offline validation requirements remain; solver uncertainty must not be disguised as physical infeasibility.

Numerical solver states and commands use fixed body-centred inertial axes at the capture epoch. KSP world axes are not assumed inertial across updates: sample the three body-fixed surface basis vectors at capture and live acquisition; map current world components into the capture basis and apply the physical planetary rotation through elapsed UT. Orbital velocity already represents inertial velocity in the current axes, not the derivative of world coordinates; rotate components only. Inverse-transform commands at current UT and ground-point radials at their predicted UT into current body axes before attitude, terrain, forecast and fallback queries. Replans preserve the original frame; no ad hoc resets. Validate against the recorded rotating-world rejection, nonrotating and changed world orientations, and consistent live state and command round-trips. Use explicit temperature/pressure units and verified KSP world-position API; compare density to runtime evidence rather than silently inventing an atmosphere. These are requirements, not claims that every configuration is already implemented or validated.


## Authoritative KSP atmosphere and aerodynamic inputs (2026-11-27)

KSP defines the planetary atmosphere; it is not an unknown physical environment requiring invented atmospheric characteristics or empirical tuning. Production guidance and named-body offline acceptance fixtures SHALL use the authoritative effective KSP body definition and atmosphere evaluation, including installed modifications where applicable. Reuse the established KSP/MechJeb re-entry simulation APIs, curves, interpolation, temperature model and force conventions wherever suitable; inspect their actual implementation before introducing replacement approximations.

- Acquire body radius, gravity parameter, rotation, atmosphere ceiling, pressure versus altitude, temperature versus altitude and applicable latitude/solar/seasonal terms, molar mass and other parameters required by the stock density, sound-speed and aerodynamic calculations. Use the correct coordinate frame, epoch and units (SI internally, explicitly convert KSP pressure units).
- Use stock aerodynamic force conventions and runtime-derived vessel drag cubes, occlusion, orientation, Mach-dependent coefficients and passive lift where applicable. Distinguish defined atmospheric properties from vessel-specific aerodynamic capability. Do not invent a density curve, constant temperature, arbitrary drag coefficient or other surrogate and present it as Duna (or another named body's actual physics).
- Obtain effective data from KSP runtime or authoritative installed definitions/curves, recording source, game/mod version and units. Make the immutable offline evaluator reproduce KSP atmosphere outputs at representative altitudes, locations and epochs, including vacuum and the atmosphere boundary; compare pressure, temperature, density and relevant aerodynamic forces against independently evaluated KSP references. Resolve mismatches before claiming physical-model parity. Document any deliberately reduced-order approximation, measured error and applicable domain; validate that it is adequate for planning and tracking.
- Synthetic atmospheres remain appropriate for explicitly synthetic analytical/unit tests only. They cannot substitute for the actual named-body atmosphere in realistic landing acceptance tests. A captured erroneous model is useful as a historical failure regression, not authoritative atmospheric truth. Missing material inputs must be acquired or explicitly reported; do not silently invent them. No repeated landing flight solely to rediscover atmospheric characteristics already defined by KSP.
- The actual-Eagle and varied-vessel acceptance tests must use verified effective atmospheric inputs and demonstrate successful targeted touchdown, not merely execution of the search. Search failure under a suspect atmosphere does not establish physical infeasibility. This requirement does not weaken any existing offline acceptance, safety or deployment gate.


## Mandatory worker execution rules — prohibited development failure modes (2026-11-27)

The assigned outcome is a functioning landing-guidance DLL suitable for iterative KSP **flight testing**. Flight testing means the user selects a target, clicks the ordinary **Land at target** button, and the guidance attempts and completes a physically feasible targeted landing; the user then supplies logs for analysis and iterative improvement. It does not mean testing whether an unfinished controller initializes, acquires data, passes admission, or can run a search. No guarantee of actual flight success is implied before flight testing, but a candidate must have a demonstrated reasonable expectation of success through the mandatory offline acceptance gate. These rules bind all implementation workers and successor chats.

Workers MUST NOT:

1. **Advance milestones prematurely.** Do not treat writing a component, increasing a version number, or implementing later-stage infrastructure as satisfying earlier milestone exit criteria. Record actual acceptance status against M0–M9 independently of build labels; return to unresolved prerequisites when they prevent landing.
2. **Substitute activity tests for outcome tests.** Do not count successful initialization, snapshot acquisition, nonzero candidate counts, search execution, or synthetic unit-test passes as proof of landing capability. Realistic reachable-case acceptance tests must assert actual propagated safe targeted touchdown with the specified miss, contact-state, fuel, clearance, and execution constraints. Do not weaken or replace a failed acceptance assertion with a diagnostic assertion that merely establishes that code ran.
3. **Invent known physical inputs or silently assume capabilities.** Do not replace authoritative effective KSP atmospheric/body physics, engine characteristics, resources, aerodynamic geometry, or measured/runtime-derivable vessel capabilities with fabricated values. Follow the authoritative-input and vessel-independent contracts above. Use the user's vessel as a regression case, not as the design envelope. If essential configuration cannot be acquired from available evidence or KSP definitions, ask the user explicitly rather than guessing.
4. **Mistake experimental inclusion for demonstrated effectiveness.** Workers are encouraged to implement, integrate, replace and actively select new or unproven optimisation algorithms in the executable guidance under development, so that their effectiveness can be tested. Prior proof of effectiveness is NOT a prerequisite to inclusion or promotion into the experimental controller; do not use the benchmark or milestone sequence to block experimentation. Evaluate the resulting implementation against realistic landing cases and the common solver-selection criteria; retain, improve, combine or replace techniques according to evidence. Do not claim a technique is effective or the resulting DLL suitable for landing flight testing merely because it runs or succeeds on easy fixtures. The complete candidate, not each novel technique in isolation, must meet the applicable offline delivery gate. Do not confuse search exhaustion with physical infeasibility or repeatedly expand an inadequate search without diagnosing its cause.
5. **Stop at intermediate engineering outputs.** Do not end an implementation assignment merely because compilation succeeds, CI focused tests pass, documentation is updated, a DLL is packaged, or one earlier defect is fixed. These are intermediate results. Continue the implementation–test–diagnose–repair cycle while executable work remains possible. A failed realistic reachable-case landing is a failed development iteration, not a completed deliverable.
6. **Transfer predictable development failures to the user.** Do not ask the user to install or flight-test a DLL already known to fail the relevant realistic landing case or with outstanding mandatory offline gate failures. Do not offer intermediate diagnostic builds as landing-test candidates. Do not require separate preview/execute buttons, special trace arming, or additional user manoeuvres as a substitute for the agreed normal workflow. Obtain missing information directly when needed; do not request another flight solely to discover defined data or reproduce a failure that can be reproduced offline.
7. **Disregard or bypass the binding plan.** Read the current design, SPEC and DEVELOPMENT before implementation; inspect the current authoritative source, relevant CI and evidence. Implement the documented objective and maintain the implementation record. Do not silently redefine completion, relax physical acceptance conditions, remove validation checks to force engagement, conceal limitations, or substitute undocumented architecture changes. Preserve safety and genuine infeasibility handling; do not force an unsafe burn merely to demonstrate activity.
8. **Misrepresent readiness or results.** Distinguish implemented, compiled, unit-tested, offline-accepted, and flight-validated states. Report failed tests, unresolved capability/model assumptions, actual candidate results, and blockers truthfully. A diagnostic fixture reproducing a known failure is useful, but cannot be represented as a successful realistic landing regression. No claim of installation readiness while the mandatory offline acceptance gate remains unmet.

### Required worker stopping and delivery criteria

- A successful compile, focused CI pass, synthetic touchdown, or isolated defect correction: continue implementation.
- A failed realistic reachable-case landing, invalid physical model, failed execution admission/tracking, or exhausted search: investigate, correct, and repeat offline. Distinguish search exhaustion from proven physical infeasibility.
- Essential missing information: retrieve it through available authoritative sources; if genuinely unavailable, request the specific information from the user. Do not stall on unrelated details.
- A genuine execution/environment/permission limit: report the exact blocker, completed evidence and remaining next action. Preserve continuity in DEVELOPMENT.md; do not claim completion, promise background work, or issue a knowingly unsuitable substitute DLL.
- Deliver a flight-test DLL only after successful realistic targeted landing and production execution-path tests, including the actual Eagle case and varied supported vessel configurations, authoritative KSP physics, independent replay, uncertainty checks, relevant regression checks, and verified build identity, consistent with the existing mandatory offline gate. Then request normal in-game landing and logs for genuine flight validation and refinement. A request for a DLL to test is not a waiver of these prerequisites.

These are mandatory execution and acceptance rules, not optional recommendations. They supersede any interpretation of earlier experimental build delivery practices that allowed intermediate diagnostic artifacts to be presented as suitable landing-test candidates. They do not waive existing safety, compatibility, regression, or deployment requirements.

### Reasonable expectation of successful flight testing

The governing delivery criterion is a reasonable, evidence-based expectation that the submitted DLL will successfully perform the intended landing using the ordinary Land at target workflow under the intended test conditions. Flight testing is not a demand for certainty or prior proof of in-game success; its purpose is to discover residual uncertainties and improve the guidance from actual flight evidence. Before submission, workers must actively review the implementation, physical assumptions, offline results and intended test scenario for shortcomings that could reasonably be identified and addressed. This includes implicit shortcomings revealed by the evidence, not just explicitly recorded bugs or failed tests. If there is no reasonable expectation of successful landing, identify and remedy the underlying shortcomings through further implementation and offline testing, or report a genuine blocker and obtain the information needed. Passing a checklist, compilation or an absence of known failures alone does not establish that expectation. Conversely, do not obstruct experimentation or demand certainty, exhaustive proof or unrelated improvements before a flight test. The existing applicable offline acceptance requirements remain evidence supporting the readiness decision, not a substitute for engineering judgement.

Spherical-coordinate powered feedback candidate is active in experimental direct and high-crossrange search alongside Cartesian feedback. This does not change the governing flight-test readiness criterion.


### Planetary terrain is a planning input (2026-11-27)

Terrain is a defined planetary characteristic, not an exceptional condition or an arbitrary validation constraint. Acquire relevant effective terrain from KSP (including installed modifications), represent its elevations in body-fixed coordinates at appropriate engineering resolution, and use them in trajectory propagation, clearance/contact constraints, optimisation, replay and execution. A safe path above higher terrain is not rejected solely because it disagrees with a target-elevation sphere. If independent actual-terrain sampling exposes a real collision, insufficient clearance or terminal surface mismatch, acquire/refine the relevant data and replan automatically while physically safe to do so. Distinguish a model-resolution/search limitation from physical infeasibility. No silently replacing actual terrain by a single target elevation or simply stopping on ordinary terrain variation. Terrain acquisition and solving must respect main-thread and real-time budgets; offline acceptance must cover uneven terrain, real collision, safe higher ground, refinement and continuation. Sampled terrain is an approximation; do not claim continuous PQS/collider certification from sparse samples. User workflow remains Land at target.


### Progressive prediction fidelity and reuse of airless guidance (2026-11-27)

The existing non-atmospheric landing guidance is a required design-review reference, including TargetAwareTerrainCache, TargetAwareBrakingPolicyContext and TargetAwareTerminalTerrainProbe. Reuse their engineering principles: coarse orbital/plane-change/deorbit targeting where detailed topography cannot affect the manoeuvre, body-fixed demand-loaded terrain around the predicted approach, higher fidelity when clearance, braking and contact depend on it, and refreshed predictions following actual manoeuvres. Do not impose expensive fine-resolution terrain calculations on every high-altitude propagation step or require an exact terminal solution for each rough orbital seed. Retain a feasible approach check before irreversible commitment; a coarse prediction is a timing/geometry hint, not execution authority. Actual terrain, clearance, contact and fuel constraints remain binding. Sampled models are not continuous PQS/collider proof. Design reviews must examine existing relevant airless implementations and document reusable approaches and material differences, rather than independently rediscovering their established solutions.
